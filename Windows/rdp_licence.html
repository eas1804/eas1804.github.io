Ошибка лицензирования 0xf06 

При попытке клиента подключиться, произошла ошибка лицензирования (лицензирование прервано по таймауту).
Попытайтесь подключиться к удаленному компьютеру снова.

Код ошибки: 0xf06
  1. Проверьте доступность сервера с компьютера пользователя:

    Test-NetConnection 10.10.18.3 -Port 3389

    Если TcpTestSucceeded : False, сначала проверяйте VPN, маршрут и доступность RDP-порта. Если True — это подтверждает только установление TCP-соединения; продолжайте диагностику.

  2. Проверьте прохождение крупных пакетов через VPN:

    ping 10.10.18.3 -f -l 1380 -n 4

    ping 10.10.18.3 -f -l 1400 -n 4

    В нашем случае пакеты с нагрузкой 1380 байт проходили, а 1400 — нет. Если картина повторится, можно проверить влияние MTU.

  3. Определите индекс VPN-интерфейса и его текущий MTU:

    Get-NetIPAddress -IPAddress 172.31.30.4 | Select-Object IPAddress, InterfaceIndex, InterfaceAlias

    Get-NetIPInterface -AddressFamily IPv4 | Where-Object { $_.InterfaceAlias -like '*OpenVPN*' } | Select-Object InterfaceIndex, InterfaceAlias, NlMtu, ConnectionState

    Индекс и адрес могут измениться после переподключения. Запишите исходное значение NlMtu, чтобы при необходимости восстановить его.

  4. Временно уменьшите MTU нужного интерфейса до 1400. На этот раз его индекс был 8. В PowerShell от имени администратора:

    netsh interface ipv4 set subinterface 8 mtu=1400 store=active

    Подставьте актуальный индекс. Если вы подключены к пользователю через тот же VPN, сеанс может прерваться — желательно, чтобы пользователь был рядом с компьютером.

  5. Повторите подключение к 10.10.18.3. Если появится ошибка 0x808 с сообщением о невозможности создать хранилище лицензий, один раз запустите mstsc от имени администратора и подключитесь с обычной учётной записью пользователя сервера.
  6. Проверьте обычный запуск RDP-клиента. В нашем случае после одного запуска с повышенными правами пользователь смог войти без них.

    Если понадобится отменить временное изменение, восстановите записанное исходное значение. В этот раз оно было 1500:

    netsh interface ipv4 set subinterface 8 mtu=1500 store=active

    Эта последовательность восстановила доступ в нашем случае. Влияние MTU остаётся вероятной причиной: окончательно подтвердить его можно, если после возврата к прежнему MTU ошибка снова появится, а при 1400 исчезнет. Изменение с store=active временное и может не сохраниться после перезагрузки или переподключения VPN.

Можно MTU задать сразу в файле .ovpn

pull-filter ignore "tun-mtu "

Проверить результат изменения MTU на 1400

netsh interface ipv4 show subinterfaces | findstr OpenVPN

Для Mac OS

macOS это можно сделать через Терминал. У VPN-интерфейса вместо индекса обычно имя вида utun4 или utun5.

  1. Найдите интерфейс OpenVPN

    Сначала подключите OpenVPN, затем выполните:

    route -n get 10.10.18.3

    В выводе найдите строку:

    interface: utun4

    Здесь utun4 — пример. У вас номер может быть другим. Команда показывает интерфейс, через который Mac направляет трафик к 10.10.18.3.

    Проверьте его параметры:

    ifconfig utun4

    Замените utun4 на своё значение. В первой строке будет указан текущий MTU, например:

    utun4: flags=8051 mtu 1500

    Запишите исходный MTU, чтобы при необходимости восстановить его. Если VPN-адрес на Mac тоже 172.31.30.4, он должен отображаться в параметрах интерфейса. manp.gs

  2. Временно установите MTU 1400

    Подставьте имя своего интерфейса:

    sudo ifconfig utun4 mtu 1400

    Введите пароль учётной записи администратора Mac. При вводе символы пароля не отображаются — это нормально.

    Проверьте результат:

    ifconfig utun4 | head -n 1

    Должно отображаться mtu 1400.

    Важно: если вы управляете Mac через этот же VPN, соединение может прерваться. При переподключении OpenVPN интерфейс может получить другое имя, а MTU — вернуться к исходному значению.

  3. Проверьте связь

    Обычный ping:

    ping -c 4 10.10.18.3

    Аналог вашей команды Windows с запретом фрагментации:

    ping -D -s 1380 -c 4 10.10.18.3

    Обратите внимание: нагрузка 1380 байт вместе с заголовками IPv4 и ICMP составляет 1408 байт, поэтому при MTU 1400 такой пакет не должен пройти без фрагментации. Для проверки непосредственно размера MTU 1400 используйте нагрузку 1372:

    ping -D -s 1372 -c 4 10.10.18.3

    Ответы покажут, проходит ли пакет этого размера по маршруту; отсутствие ответов само по себе ещё не доказывает проблему с MTU.

  4. Как вернуть исходное значение

    Например, если до изменения было 1500:

    sudo ifconfig utun4 mtu 1500

    Подставьте записанное ранее значение и актуальное имя интерфейса.

Проблемы с сервером Лицензиррования

Журнал сервера лицензирования (RD Licensing)

eventvwr.msc ->Applications and Services Logs -> Microsoft -> Windows -> TerminalServices-Licensing -> OperationalТакже

Классический журнал System

(фильтр по источнику TerminalServices-Licensing

Ключевые Event ID, которые стоит искать:

  1. Event ID 21: Ошибка выдачи временной/постоянной лицензии клиенту.
  2. Event ID 1028 / 1029: Сервер лицензирования не смог обновить или предоставить RDS CAL для устройства.
  3. Event ID 1043: Отказ в выдаче лицензии из-за отсутствия свободных CAL или истечения срока действия.

Журнал RDP-хоста (RD Session Host)

На этом же сервере перейдите в журнал самого RDP-сервиса:

Applications and Services Logs -> Microsoft -> Windows -> TerminalServices-RemoteConnectionManager -> OperationalКлючевые Event

  1. ID:Event ID 1004: Terminal Server не может выдать лицензию клиенту (в описании ошибки будет указан имя/MAC вашего Mac).
  2. Event ID 1011: Ошибка проверки лицензии при установке соединения.

Powershell

Get-WinEvent -FilterHashtable @{
    LogName = 'System', 'Microsoft-Windows-TerminalServices-Licensing/Operational', 'Microsoft-Windows-TerminalServices-RemoteConnectionManager/Operational'
    Level = 2, 3 # Error и Warning
} -MaxEvents 30 | Format-Table TimeCreated, Id, ProviderName, Message -AutoSize

Остановить службу лицензирования RDS

Stop-Service TermServLicensing -Force

Запуск службу лицензирования RDS

Start-Service TermServLicensing

Сделать копию TLSLic.edb

Остановка службы занимает 1–2 секунды и не рвет активные RDP-сессии пользователей, которые уже работают на сервере. 
Stop-Service TermServLicensing -Force
Copy-Item -Path "C:\Windows\System32\LServer\TLSLic.edb" -Destination "C:\Windows\System32\LServer\TLSLic.edb.bak"
Start-Service TermServLicensing
